MAPLESTORY IDLE OPTIMIZER — GITHUB BUILD AND RELEASE SETUP
===========================================================

The repository includes .github/workflows/build-desktop-releases.yml. GitHub
provides native Windows and Linux runners, installs build dependencies, stages
Tesseract OCR, runs tests and packaged startup checks, and uploads the results.

MANUAL TEST BUILD
-----------------
Open GitHub Actions, select Build Desktop Releases, and select Run workflow.
This produces downloadable Windows and Linux artifacts without creating a public
GitHub Release.

TAGGED RELEASE
--------------
Pushing a tag that exactly matches APP_VERSION, such as v3.0.0, builds both
platforms and publishes a GitHub Release automatically. Release notes are
generated by GitHub from commits; no standalone per-version update-note file is
needed.

FIRST-TIME REPOSITORY SETUP FROM LINUX
--------------------------------------
1. Create an empty GitHub repository. A private repository is fine.
2. Extract this package and open a terminal in its root.
3. Initialize and push the repository:

       git init
       git branch -M main
       git add .
       git commit -m "Initial MapleStory Idle Optimizer release"
       git remote add origin git@github.com:YOUR_USERNAME/YOUR_REPOSITORY.git
       git push -u origin main

4. Run the Build Desktop Releases workflow manually once and test both artifacts.
5. Push the matching version tag when ready.

FUTURE RELEASES
---------------
1. Change APP_VERSION in maplestory_idle_companion_optimizer.py.
2. Add the new release summary to the single README.txt changelog. Do not create
   a separate FEATURE_NAME_X.Y.Z.txt, README_X.Y.Z.txt, or release-notes TXT.
3. Run ./publish_release.sh from the repository root.

publish_release.sh validates and locally tests Linux, commits all source changes,
pushes main, and pushes the matching tag. It also deletes legacy root-level
per-version update-note files before committing, so old tracked copies disappear
from the current GitHub branch on the next release.

RELEASE ASSETS
--------------
Each platform contributes:
- the final single-file executable;
- a compressed one-folder diagnostic build;
- a SHA256SUMS file.

The workflow does not attach a standalone README/update-note TXT. Documentation
remains in the repository, while GitHub supplies generated release notes.

LOCAL BUILDS
------------
Linux: ./build_tools/build_linux.sh
Windows: build_tools\build_windows.bat
Upload-ready outputs are written to release/.

WORKFLOW SECURITY
-----------------
Normal build jobs receive read-only repository access. Only the tagged release
job receives contents: write permission, solely to create the GitHub Release and
upload its assets using GitHub's short-lived token.

TROUBLESHOOTING
---------------
- No Run workflow button: confirm the workflow is on the default branch and
  Actions are enabled.
- Tag validation failure: the tag must be v followed by APP_VERSION.
- A platform build fails: inspect the failed test, OCR staging, packaging, or
  smoke-test step in that job.
- Windows SmartScreen warning: the executable is unsigned.
